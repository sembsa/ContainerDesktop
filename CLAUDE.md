# Container Desktop — project guide for Claude

Native macOS SwiftUI app: a Docker-Desktop-style GUI for Apple's [`container`](https://github.com/apple/container) CLI. It does **not** reimplement container logic — every action shells out to `container` and parses its JSON.

- Repo: `github.com/sembsa/ContainerDesktop` (`gh` is authenticated as `sembsa`)
- Bundle id: `com.containerdesktop.ContainerGUI` · Product/bundle name: `ContainerGUI.app` · Display name: "Container Desktop"
- Target: **macOS 26 (Tahoe)**, Apple Silicon · Swift 6 (strict concurrency) · sandbox **OFF** (spawns the external CLI → Developer ID / direct distribution, not Mac App Store)

## Build & test

Xcode project is **generated by XcodeGen** from `project.yml` (`ContainerGUI.xcodeproj` is gitignored — never edit it by hand; edit `project.yml`).

```bash
xcodegen generate
xcodebuild build -project ContainerGUI.xcodeproj -scheme ContainerGUI \
  -destination 'platform=macOS' -derivedDataPath .build -clonedSourcePackagesDirPath .spm
xcodebuild test  -project ContainerGUI.xcodeproj -scheme ContainerGUI \
  -destination 'platform=macOS' -derivedDataPath .build -clonedSourcePackagesDirPath .spm
```

- First build may need the Metal toolchain (SwiftTerm ships Metal shaders): `xcodebuild -downloadComponent MetalToolchain`.
- SwiftUI cross-file "Cannot find type X" diagnostics from the editor are false positives (no module index without the project) — trust `xcodebuild`.

## Architecture

```
SwiftUI views (Features/<X>/) → @Observable stores → ContainerCLI (actor) → Process(/usr/local/bin/container)
        │                              │                      │
   MenuBarExtra              AppModel (root: selection,   JSON (Codable) / line stream (AsyncStream)
   EmbeddedTerminalView      service state, stores)
   (SwiftTerm, PTY)
```

- `CLI/ContainerCLI.swift` — the only place that runs the binary (`json`, `run`, `run(input:)` for stdin, `runElevated` for admin, `stream` for `logs -f`/`stats`). `BinaryResolver` finds the binary (GUI apps don't inherit shell PATH). `RunCommandBuilder` maps a `RunConfiguration` to `container run` args (emits `--label`, `--network`, `--arch`, `--publish`, `--env`, `--volume`, …).
- `Models/` — `Codable` structs mirroring real CLI JSON; keys verified against live output. `Configuration` includes `labels`, `networks`, `platform`, etc.
- `Features/<Containers|Images|Volumes|Networks|Registries|Machines|System>/` — store + views per section. `Compose/` translates `docker-compose.yml` to `container run` calls (labels `compose.project` / `compose.service` drive grouping).
- Deps (SPM in `project.yml`): `SwiftTerm`, `Yams`, `Sparkle`, `libghostty-spm`.

### Terminal engines

`Terminal/` holds two engines behind `@AppStorage("terminalEngine")` (`TerminalEngine`, default `swiftTerm`):

- **SwiftTerm** — CoreText, spawns the PTY itself. The default.
- **Ghostty (libghostty)** — Metal rendering. `GhosttyTerminalView` hands `container exec -it <id> sh` to libghostty's `.exec` backend as a ghostty `command` config line; libghostty owns the PTY, resizing and the exit report. Opt-in because **libghostty's embedding API is explicitly not stabilized** ("used primarily by the macOS app, may change significantly between releases") and Ghostty publishes only `ghostty-vt` officially — the full library comes from a third-party build, so the package is pinned with `exactVersion`, never `from:`.

Two things that will bite when touching this: libghostty runs the command through `login -flp <user> /bin/bash --noprofile --norc -c exec -l <cmd>`, so (a) the command must stay a plain executable + arguments — a bare `clear; …` gets torn apart, hence the `/bin/sh -c "clear; exec …"` wrapper in `TerminalCommandLine`, and (b) without that `clear` the host's "Last login: … on ttysNNN" shows up above the container's prompt. The XCFramework is a **static** library, so nothing extra needs signing.

## Localization (important)

- Localizations: `ContainerGUI/Resources/{en,pl,zh-Hans}.lproj/Localizable.strings`. **Keys are the Polish source strings**; each file maps key → translation (pl = identity).
- `developmentLanguage`/`CFBundleDevelopmentRegion = en` and `CFBundleLocalizations: [en, pl, zh-Hans]` → non-Polish/Chinese systems fall back to **English** (this is the fix for issue #1; do not revert to `pl`).
- Settings has an in-app language switch (writes `AppleLanguages`).
- **When you add/change UI text**: add the Polish key to **all three** `.strings` files (use the Polish literal as key; provide en + zh-Hans values). `Text("…")` and `String(localized: "…")` both localize via these files. Verify with `plutil -lint`. Test a language with `defaults write com.containerdesktop.ContainerGUI AppleLanguages '("zh-Hans")'` then relaunch (delete the key to reset).

## Versioning & auto-update (Sparkle) — get this right

- `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` live in `project.yml > settings.base`; `info.properties` wires `CFBundleShortVersionString = $(MARKETING_VERSION)` and `CFBundleVersion = $(CURRENT_PROJECT_VERSION)`. (If these aren't wired, the app shows the stub "1.0 (1)".)
- **Sparkle compares `CFBundleVersion`** to decide if an update is newer, so **`CURRENT_PROJECT_VERSION` MUST strictly increase every release** (e.g. 0.2.3 → build 2, 0.2.4 → build 3).
- Auto-update keys in `info.properties`: `SUFeedURL = https://sembsa.github.io/ContainerDesktop/appcast.xml`, `SUPublicEDKey` (EdDSA public key; **private key is in the maintainer's login Keychain** — generated once via Sparkle `generate_keys`), `SUEnableAutomaticChecks`. "Check for Updates…" is in the app menu (`CommandGroup(after: .appInfo)`) and the menu-bar popover (`CheckForUpdatesView`).

## Release process

1. Bump `MARKETING_VERSION` (+ **increment `CURRENT_PROJECT_VERSION`**) in `project.yml`.
2. `scripts/package.sh` → builds the Release `.app`, makes `dist/ContainerDesktop.dmg`, and runs Sparkle `generate_appcast` (signs with the Keychain EdDSA key) → updates `docs/appcast.xml`.
3. Publish the GitHub release: `gh release create vX.Y.Z dist/ContainerDesktop.dmg --title "X.Y.Z" --notes "…"`. The DMG asset **must be named `ContainerDesktop.dmg`** (the appcast enclosure points at `releases/latest/download/ContainerDesktop.dmg`).
4. Commit `docs/appcast.xml` to `main` (GitHub Pages serves it at `SUFeedURL`).
5. Verify: appcast URL returns HTTP 200 with the new `sparkle:version`; the DMG URL returns 200.
- Distribution is **ad-hoc signed, not notarized** → first launch needs *System Settings → Privacy & Security → Open Anyway* (or `xattr -dr com.apple.quarantine`). Sparkle clears quarantine on its installed updates, so updates after the first install are seamless.
- **Caveat**: builds older than ~mid-June (no Sparkle) cannot auto-update — they must be replaced manually once.
